# HelixSQL mutation language: research and implementation plan

Status: proposed language design; no mutation functionality implemented.
Research date: 2026-09-27.

## 1. Recommendation

Extend this app's existing HelixSQL with `INSERT INTO NODES:Label` and
`INSERT INTO EDGES:Label`. Keep the familiar SQL column-list/`VALUES` structure,
use explicit `source` and `target` columns for edges, and add `RETURNING` for
created data. Use an explicit `BEGIN MUTATION … COMMIT` block with local node
bindings when creating a connected graph in one transaction.

Interpret “like SQ” as SQL-like syntax consistent with the current HelixSQL
language. `INSERT` is the entry point for creation; existing `SELECT`, `QUERY`,
`SHOW`, and `DESCRIBE` remain available for reading.

The core experience should look like this:

```sql
INSERT INTO NODES:User (name, age)
VALUES ('Alice', 30)
RETURNING id, name;

INSERT INTO EDGES:Follows (source, target, since)
VALUES (42, 43, 2026)
RETURNING id, source, target;
```

These are two independent examples. IDs `42` and `43` represent nodes that
already exist; they are not assumed to be the IDs generated by the first example.

## 2. What exists in this repository

The design builds on the following inspected code, rather than introducing a
second parser in the frontend:

The README describes entity IDs as `i64`; the compiler also parses numeric
literals as signed integers or floats. This matters for the protocol decision below.

## 3. Research and design choices

### SQL gives us the basic shape

PostgreSQL documents column lists, multi-row `VALUES`, generated-value retrieval
with `RETURNING`, and conflict handling tied to unique constraints/indexes.
Adopt the first three concepts. Defer conflict syntax until the backend can
actually enforce its semantics under concurrency. This is an intentional small
SQL-like dialect, not a claim of PostgreSQL compatibility.
[Source: PostgreSQL INSERT](https://www.postgresql.org/docs/current/sql-insert.html).

### Graph creation needs explicit identity and direction

Cypher supports creating nodes and directed relationships, binding them to
variables, and using `INSERT` as a GQL-oriented synonym for `CREATE`. Its pattern
notation is expressive, but adopting it would add a second graph syntax alongside
this app's existing `NODES:Label`/`EDGES:Label` vocabulary. Borrow bindings and
explicit relationships, while retaining HelixSQL's vocabulary.
[Source: Cypher CREATE and INSERT](https://neo4j.com/docs/cypher-manual/current/clauses/create/).

SurrealQL's `RELATE` makes direction visible and supports edge properties, but
collection endpoints can multiply relationships. Its documented default also
allows relationships whose endpoint records do not exist. For this language,
require one existing node per endpoint and one edge per input tuple; endpoint
existence must be enforced transactionally.
[Source: SurrealQL RELATE](https://surrealdb.com/docs/reference/query-language/statements/relate).

### HelixDB supports the intended execution model

Current official documentation shows a write batch containing named `add_n`
results followed by `add_e` using those variables. It states that batch entries
commit or roll back together. This is a strong fit for local bindings and an
atomic mutation block. It also documents property setting/removal and entity
deletion as later mutation building blocks.
[Source: HelixDB writing data](https://docs.helix-db.com/database/helix-db/query-guides/writing-data).

The documented data model has one label per entity, separate unsigned 64-bit
node/edge ID spaces, directed edges, parallel edges, and self-loops. Properties
can include scalars, arrays, and objects. Unique equality indexes are available
for nodes, not edges. Keep node references distinct from edge references and do
not infer uniqueness from an edge's endpoints and label.
[Source: HelixDB data model](https://docs.helix-db.com/database/helix-db/core-concepts/data-model).

### Critical compatibility finding

The app emits flat traversal batches to `/v1/query`. Current public HTTP docs
describe `/v2/query` with nested operation trees and matching `request_type` and
`query.read`/`query.write` variants. They also distinguish requiring a writer
from waiting for durable writes. These docs do **not** establish write support
for this app's existing v1 endpoint.
[Source: HelixDB HTTP API](https://docs.helix-db.com/database/helix-db/query-guides/http-api).

**Decision:** target the documented v2 write contract for new mutation support.
Keep existing v1 reads working. Before enabling mutations on a connection,
verify its server version and contract and supply matching v2 read support for
viewing the inserted graph. A legacy v1 write adapter is a separate deliverable
only if the actual target server's source/contract proves it is supported.
Do not guess a flat v1 write envelope, or replay a failed write against another
endpoint as a fallback.

Research used official documentation; no live HelixDB mutation or deployed-server
compatibility test was performed for this plan. The writing-data, data-model,
parameters, and secondary-index pages were retrieved through their official
Markdown endpoints when the browser fetch could not open the HTML pages.

## 4. Language structure

### A. Insert nodes

```sql
-- One node.
INSERT INTO NODES:User (name, age, active)
VALUES ('Alice', 30, TRUE)
RETURNING id, label, name;

-- Multiple nodes with the same property columns.
INSERT INTO NODES:User (name, age)
VALUES ('Alice', 30), ('Bob', 28), ('Cara', 35)
RETURNING id, name;

-- A node with no explicit properties.
INSERT INTO NODES:Topic DEFAULT VALUES
RETURNING *;

-- Reuse existing quoting rules.
INSERT INTO NODES:"Research Group" ("display name", "id")
VALUES ('Graph systems', 'external-123')
RETURNING id, "id" AS external_id;
```

Rules:

- A label is mandatory and case-sensitive. Keywords are case-insensitive.
- Explicit columns are mandatory for `VALUES`; there is no sampled-schema column order.
- Each tuple creates exactly one entity. Tuple width must match column count.
- Reject duplicate property columns, including quoted/unquoted spellings that
  resolve to the same property key.
- The database generates internal IDs. Unquoted `id`, `label`, `score`, and
  `distance`, and explicit virtual paths such as `$id`, are not writable properties.
- Quoted names such as `"id"` denote ordinary properties, following existing
  HelixSQL read behavior. Quote other reserved virtual-column names similarly.
  Explicit internal `$…` paths remain forbidden in write property maps.
- `DEFAULT VALUES` creates one node with an empty supplied property map. It does
  not infer defaults from the schema sidebar. Any actual defaults belong to the server.
- Omitted properties are absent. `NULL` is an explicit null value, not an instruction
  to omit or remove a property. Verify null preservation in backend contract tests.
- New labels/properties are allowed unless the server's authoritative constraints
  reject them; absence from a sampled schema is not a validation error.

### B. Insert directed edges

```sql
INSERT INTO EDGES:Follows (source, target, since)
VALUES (42, 43, 2026)
RETURNING id, label, source, target, since;

-- Each tuple is one explicit endpoint pair.
INSERT INTO EDGES:Follows (source, target)
VALUES (42, 43), (42, 44), (43, 44);

-- An edge may have a property whose name resembles endpoint metadata.
INSERT INTO EDGES:ImportedFrom (source, target, "source")
VALUES (42, 43, 'crm')
RETURNING source, "source" AS import_source;
```

Rules:

- Require exactly one unquoted `source` and one unquoted `target` column.
  Column order is arbitrary; quoted `"source"`/`"target"` are ordinary properties
  and do not satisfy the endpoint requirement.
- Endpoint values are node IDs, node-ID parameters, or earlier local node bindings.
  Plain integers in endpoint positions always mean node IDs, even when an edge
  has the same numeric ID. An edge binding is a type error.
- Direction is `source → target`. No implicit inverse edge is created.
- Both nodes must exist in the transaction, including nodes created earlier in
  the same block. Missing endpoints fail the entire statement/block.
- Reject null, floating-point, string-literal, array, or object endpoints.
- Parallel edges and self-loops are permitted subject to backend validation.
  Repeating an insert creates another edge; it is not an implicit upsert.
- No endpoint selectors, automatic node creation, list expansion, or Cartesian
  products in the first release. Bulk edges use explicit tuples.

An alternative `INSERT EDGE … FROM … TO … SET …` would read naturally, but it
duplicates the bulk form. Start with one canonical edge syntax and revisit
shorthand only after real editor usage shows a need.

### C. Create a connected graph atomically

```sql
BEGIN MUTATION;
  INSERT INTO NODES:User AS alice (name)
  VALUES ('Alice')
  RETURNING id, name;

  INSERT INTO NODES:User AS bob (name)
  VALUES ('Bob')
  RETURNING id, name;

  INSERT INTO EDGES:Follows (source, target, since)
  VALUES (@alice, @bob, 2026)
  RETURNING id, source, target;
COMMIT;
```

`AS alice` binds the inserted node entity, independently of its `RETURNING`
projection. `@alice` is a typed node reference, not string substitution and not
an arbitrary expression. Bindings are available only inside their block, are
case-sensitive, cannot be reassigned or forward-referenced, and must bind exactly
one node. Reject `AS` on multi-row inserts and edge inserts in the first release.
Allow `AS` on a node `DEFAULT VALUES` insert.

Treat the entire block as one editor request and one database write transaction.
Require semicolons between block statements. Do not implement persistent sessions
where the user runs `BEGIN` and `COMMIT` in separate clicks. Reject nested blocks,
standalone `COMMIT`, empty blocks, and multiple unwrapped statements.

Every block statement receives an ordered result entry identified by statement
index. A later edge error must roll back earlier node inserts. Never emulate this
with separate committed HTTP calls followed by best-effort deletion.

### D. Bind data separately from source text

```sql
INSERT INTO NODES:User (name, age)
VALUES (:name, :age)
RETURNING id;

INSERT INTO EDGES:Follows (source, target)
VALUES (:from_id, :to_id);
```

Use `:name` for supplied parameters, `@name` for local entity references, and
retain `$id`/`$label` for existing virtual fields. The parser distinguishes the
label colon in a target from a parameter colon in a value position.

Add a typed bindings map to compile/run IPC. Use decimal strings with explicit
integer/node-ID types for values that JavaScript cannot represent exactly.
Rust validates and serializes them without conversion through a JS `number`.
Keep labels, property names, and syntax non-parameterizable in the initial version.
Reject missing parameters and incompatible reuse of one parameter across types.

HelixDB documents parameter values separately from their type declarations.
Confirm the endpoint-reference encoding specifically: the documented general
parameter family list does not itself establish a full-range `u64` node-ID
parameter type. If necessary, lower a validated ID parameter to a typed endpoint
constant in Rust; never substitute its text into the SQL source.
[Source: HelixDB parameters](https://docs.helix-db.com/database/helix-db/query-guides/parameters).

### E. Return results without repeating writes

- No `RETURNING`: show a mutation receipt with inserted-node and inserted-edge
  counts, confirmed transaction outcome, and duration; do not display a row table.
- `RETURNING id, name`: return only those columns for each inserted entity.
- Allow `AS` on returned columns to disambiguate metadata from properties.
  Reject duplicate output names unless the user gives distinct aliases.
- `RETURNING *`: return complete created entities with identity/endpoint metadata
  separate from a nested `properties` object, avoiding collisions with properties
  named `id`, `source`, or `target`.
- No aggregates, traversal, ordering, expressions, or limits inside `RETURNING`
  in the first release. Return input tuple order, reconstructed through internal
  row bindings if the backend does not guarantee it.
- Creation executes once per input tuple. Bind the created entity, then project
  from that binding in the same transaction when needed. Never copy an `add_n`
  or `add_e` tree into separate property/identity projections.
- A successful commit and a failed graph refresh are separate outcomes. Preserve
  the successful receipt if later read-only UI refresh fails.

## 5. Initial grammar

This EBNF describes the proposed insert grammar, not currently accepted syntax.
Existing read statements keep their grammar. Keywords are shown in uppercase;
`identifier`, `string`, and numeric tokenization retain current quoting/comment rules.

```ebnf
mutation_input = insert, [";"] | mutation_block ;
mutation_block = "BEGIN", "MUTATION", ";", insert, ";",
                 { insert, ";" }, "COMMIT", [";"] ;

insert        = node_insert | edge_insert ;
node_insert   = "INSERT", "INTO", "NODES", ":", identifier,
                ["AS", binding_name], node_data, [returning] ;
edge_insert   = "INSERT", "INTO", "EDGES", ":", identifier,
                column_values, [returning] ;
node_data     = column_values | "DEFAULT", "VALUES" ;
column_values = "(", identifier, {",", identifier}, ")",
                "VALUES", tuple, {",", tuple} ;
tuple         = "(", value, {",", value}, ")" ;
value         = scalar | parameter | node_binding ;
scalar        = string | integer | finite_float | "TRUE" | "FALSE" | "NULL" ;
parameter     = ":", binding_name ;
node_binding  = "@", binding_name ;
returning     = "RETURNING", ("*" | return_item, {",", return_item}) ;
return_item   = column_ref, ["AS", identifier] ;
```

`column_ref` reuses existing property/virtual-field resolution. A `binding_name`
is an unquoted ASCII name matching `[A-Za-z_][A-Za-z0-9_]*`, with reserved keywords
excluded. Semantic validation restricts bindings to blocks, node references to
endpoint positions, and endpoints to unsigned integer IDs. These restrictions
are intentionally separate from the shared value grammar.

Keep integer token text exact until its semantic type is known: ordinary integer
properties initially use `i64`, while v2 entity IDs require `u64` including zero.
Reject overflows instead of falling back to floats. All IPC IDs remain strings.
Before shipping full-range IDs, update read predicates, `DESCRIBE`, decoding,
schema-generated queries, and graph lookup paths too; a created ID must remain
usable everywhere in the application.

Start property literals with strings, signed integers, finite floats, booleans,
and null. Arrays, objects, date-time, bytes, and vector literals need separate
syntax/type proposals and contract tests; do not silently store them as strings.

## 6. Compiler and execution architecture

```text
source + typed parameters
        ↓
lexer / parser → mutation AST with spans
        ↓
semantic validation + binding resolution + exact numeric validation
        ↓
ordered mutation plan (create once, bind entities, project results)
        ↓
verified protocol adapter → one write request
        ↓
mutation receipt + optional rows/entities → table / graph refresh
```

Recommended AST concepts:

- `InsertNode`: label, property columns, rows/default-values, optional local
  binding, optional returning projection, and spans.
- `InsertEdge`: label, typed source/target references per row, properties,
  optional returning projection, and spans.
- `MutationBlock`: ordered insert statements plus its binding scope.
- `NodeReference`: exact node ID, typed parameter, or bound node.
- `Returning`: explicit columns/aliases or full entities.
- `ExecutionKind`: read or write, propagated through compilation and execution.

Keep parse-time syntax separate from the validated plan. For example, an arbitrary
parsed value is not a valid `NodeReference` until validation succeeds. Keep all
parsing, binding, lowering, and response decoding in Rust.

Use internal names independent of user bindings and returned column names.
Bulk inserts lower to individually identified creations within one batch unless
the verified server supplies an equivalent bulk primitive. Never split a bulk
statement across separately committed batches behind the user's back.

For v2, the documented envelope is structurally:

```text
request_type: write
query.write.entries:
  named node creation(s)
  named edge creation(s) referring to node identities
  projections/counts over those named results as required
query.write.returns:
  the requested receipt/projection bindings
```

This is a conceptual mapping, not a proposed new server API. Generate exact JSON
from the version-pinned HelixDB contract. Verify entity-reference behavior after
projection; a returned property map must not replace a node binding needed by
a later edge.

`compile_query` remains side-effect-free. Its view model should include execution
kind, protocol, planned insert counts, parameter requirements, and a wire preview
when fully bound. Mark planned counts as estimates until execution succeeds.
The Rust execution path derives read/write behavior from its own compiled plan,
not a client-supplied flag.

For writes, require writer execution independently of the existing read routing
preference. Make durability policy explicit and test the selected server's
acknowledgment behavior. Do not label acknowledgment as durable unless guaranteed.

Timeouts, lost connections after submission, and unrecognized post-submit failures
can leave an unknown outcome. Preserve this distinction from confirmed rollback,
and never automatically retry a plain insert. If the server confirmed commit but
the app cannot decode returned data, report committed-with-result-error rather
than inviting a retry. Idempotency must be a server-backed feature, not just an
unused client-generated request ID.

## 7. Validation and diagnostics

Continue the existing `message`, `span`, and `hint` diagnostic shape; add stable
mutation error codes and statement/tuple indexes for runtime failures when known.
Examples:

| Input problem | Expected diagnostic |
| --- | --- |
| `INSERT INTO NODES (name) VALUES ('Alice')` | Missing label; suggest `NODES:User` |
| Columns `(name, age)`, tuple `('Alice')` | Expected 2 values, found 1 |
| Edge has `"source"` but no unquoted `source` | Missing edge source endpoint |
| Endpoint `42.5` or `NULL` | Expected a node ID or local node binding |
| `@alice` before its insert | Unknown or forward-referenced binding |
| Multi-row node insert with `AS alice` | A binding must identify exactly one node |
| Missing endpoint node | Endpoint does not exist; transaction rolled back if confirmed |
| Value outside selected numeric range | Integer out of range; never round |
| `RETURNING id, "id"` | Duplicate output name; suggest a column alias |
| Multiple statements outside a block | Wrap related inserts in `BEGIN MUTATION … COMMIT` |
| Connection has no verified write adapter | Unsupported mutation protocol; do not submit |

Set explicit limits for statement count, input rows, request bytes, and returned
data. Reject over-limit atomic requests before submission, rather than truncating
them or partially executing them. Do not reuse read defaults such as the 500-row
selection limit to silently cap writes. Pin limits after the protocol spike.

## 8. Scope after insertion

The initial release should include nodes, explicit-pair edges, multi-row inserts,
parameters, `RETURNING`, and atomic connected-graph blocks. Defer the following:

| Extension | Direction | Prerequisite |
| --- | --- | --- |
| Endpoint lookup by properties | A scalar `NODE(...)` selector using existing filtering concepts | Enforce exactly one match in the same transaction; never take the first silently |
| `INSERT … SELECT` | Insert rows or explicit source/target pairs from a read result | Defined cardinality, snapshot semantics, and write bounds |
| Node upsert | SQL-like `ON CONFLICT (key) DO NOTHING / DO UPDATE` | Active unique node index and verified atomic conflict handling |
| Unique relationship insertion | Separate explicit semantics, not ordinary `INSERT` | Backend-enforced uniqueness or equivalent transactional primitive |
| `UPDATE NODES/EDGES … SET … WHERE …` | Reuse typed values and predicate AST | Selection semantics, affected counts, concurrency behavior |
| Property removal | Explicit `REMOVE` behavior, distinct from assigning null | Verified property-removal mapping |
| `DELETE FROM NODES/EDGES … WHERE …` | Require explicit target selection | Decide restrict-versus-detach behavior and report incident-edge effects |
| Rich property/vector values | Typed arrays/objects and explicit special literals | Exact backend encodings and index dimension/type validation |
| DDL | Separate index/schema statements | Authoritative catalog and asynchronous index lifecycle handling |

Do not ship `UPSERT` by composing an ordinary read with a later insert. Unique
index readiness is also significant: the official index guide describes
asynchronous backfill and an activation lifecycle, so a requested index cannot
be assumed usable immediately.
[Source: HelixDB secondary indexes](https://docs.helix-db.com/database/helix-db/query-guides/secondary-indexes).

## 9. Implementation sequence and acceptance gates

### Phase 0 — Pin the server contract

1. Identify the target HelixDB build/version and supported query endpoints.
2. Capture versioned request/response fixtures for node insertion, edge insertion,
   named references, projection, typed values, and one deliberately failing batch.
3. Verify rollback after an earlier successful creation, missing/deleted endpoints,
   generated-ID ranges, null handling, and return behavior.
4. Verify writer/durability behavior and error outcomes. Select the connection's
   protocol through read-only discovery or explicit configuration, not test writes
   against a user's database.
5. Implement required v2 read compatibility and full-range ID support before
   exposing v2 writes in the UI. Legacy v1-only connections stay read-only.

Gate: real-server fixtures prove atomic creation and usable returned identities.
If the server cannot enforce endpoint integrity, add the necessary server-side
validation/transaction support before enabling edge inserts.

### Phase 1 — Parser, typed plan, and compile preview

Extend `hql.rs` or split its mutation pieces into focused modules as needed.
Add grammar, spans, semantic validation, parameters, local scopes, result shapes,
and read/write classification. Preserve all existing read parsing behavior.

Gate: every example above parses; malformed inputs fail with useful spans;
compile/preview makes no database calls; write JSON matches pinned fixtures.

### Phase 2 — Execute inserts and return receipts

Extend `lib.rs`, Rust result decoding, `src/client.ts`, and `src/results.ts`.
Implement one-request atomic execution, typed ID transport, returning projections,
and confirmed/unknown outcome reporting. Support literal and parameterized IDs.

Gate: one creation per tuple, no extra writes from `RETURNING *`, no automatic
retry, correct writer routing, and rollback of a failed multi-row statement/block.

### Phase 3 — Editor and graph integration

Update `QueryEditor`, `ResultsPanel`, and `App` to show “Run mutation” for writes,
display the receipt plus requested data, and expose node/edge/block examples.
Add a small typed parameter editor. Prevent duplicate submissions while a request
is in flight. Only explicit execution writes; preview, connection checks, schema
loads, and automatic graph refresh remain reads.

Refresh affected schema/graph data after confirmed success. Preserve user context
and existing graph bounds; an inserted edge does not guarantee both endpoint
nodes are already loaded. Show refresh failures separately from mutation outcomes.

Gate: creating two nodes and their edge is usable end-to-end in the desktop app,
including large IDs and a failed graph refresh after a successful commit.

### Phase 4 — Mock, regression suite, and documentation

Extend the mock with the supported contract and transaction rollback using staged
state. Keep real-server tests separate: the mock cannot prove server transaction,
writer routing, uniqueness, or protocol compatibility behavior.

Update README grammar, examples, protocol description, and read-only claims only
when the feature is implemented. Document unsupported extensions explicitly.

Gate: run the repository's Rust tests, `npm test`, and `npm run typecheck`, plus
the version-pinned real-server mutation suite. Existing read behavior passes.

## 10. Required test scenarios

- Lexer/parser: quoting, comments, escaped strings, trailing semicolons, nested
  block rejection, parameter/label colon disambiguation, and Unicode error spans.
- Validation: arity, duplicate properties, mandatory labels, reserved columns,
  valid `"id"` properties, missing endpoints, and invalid binding scopes/types.
- Numeric boundaries: zero, negative endpoint rejection, signed property limits,
  IDs above `2^53`, above `i64::MAX`, at `u64::MAX`, and overflow rejection.
- Write semantics: repeated inserts create distinct entities; parallel edges and
  self-loops behave as specified; one tuple produces one creation.
- Results: aliases remain entity references despite projections; `RETURNING *`
  causes no duplicate writes; metadata/property collisions remain distinguishable.
- Transactions: an invalid final edge rolls back preceding nodes; row failure
  rolls back bulk insertion; connection loss is not reported as guaranteed rollback.
- Concurrency: endpoint deletion races cannot produce dangling edges; no implicit
  uniqueness promises are made for parallel edge inserts.
- Transport/UI: preview never writes, v1-only connections reject unsupported
  mutations, no write endpoint fallback, no implicit retries, decimal IDs survive
  IPC, and post-commit refresh errors do not erase the success receipt.

## 11. Decisions to settle during the protocol spike

The syntax recommendation is concrete; these remaining questions depend on the
actual server contract rather than user-facing keyword preferences:

1. Which target deployments need v1 compatibility, and which support v2 reads/writes?
2. Does endpoint creation already guarantee existence under concurrent deletion?
3. How are full-range node-ID parameters encoded, and how are returned IDs typed?
4. Which result/projection operations preserve entity bindings without re-execution?
5. Which acknowledgment/durability policy should the app expose or default to?
6. What request/return limits fit the supported local and hosted deployments?

Resolve these with fixtures and real-server tests before declaring the language
executable. They do not prevent adopting the proposed SQL-like surface syntax.
